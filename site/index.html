psz-melonmix — behaviour spec

What the single-screen build is supposed to do in each state of the game, where every element on screen comes from, and how to tell a bug from a disagreement about intent.

This document is the contract. When something looks wrong, find the state below and compare against it before changing any code.
  • Behaviour differs from this page → it is a bug. Fix the code.
  • Behaviour matches this page but is still unwanted → the spec is wrong. Correct this page first, in the same change that alters the behaviour. A fix that silently contradicts the spec turns the next bug report into an argument.
  • The state is not described here → say so in the report. An undocumented state is a gap in this page, not a licence to guess.

How to read the screenshots

Every screenshot below is a single frame in compare mode (PSZ_COMPARE=1): the wide panel on the left is our output, and the small panel on the right is the untouched source — the bottom screen exactly as the game drew it. Nothing is edited between them.

That pairing is the whole verification method. Every ported element is a rectangle copied from the right-hand panel to the left one, so a mismatch is visible in one frame without needing a reference image or a second run.

State detection

Which state the build thinks it is in decides everything else, and it is decided by two reads. No overlay images, no heuristics.

TestMeaning
*(0x02108D04) == 0 Not the main game. The player object pointer is null in every other mode — shops, quest counter, title, file select, character create. Present the bottom screen whole.
*(player + 0x280) == 5 A full-screen menu is open inside the main game (main menu, item menu, Mag). Present the bottom screen whole. Normal play reads 1.
neither Field or town. Composite the four corner elements over the top screen.
CRC32 of 512 bytes at 0x0211E640 Which overlay is resident — and that is the game's mode. ov16 cutscene player, ov17 dialogue player, ov00 title and ov06 ending all carry their content on the top screen: draw nothing. ov11 create, ov12 counter/shop and ov14 file select present the bottom screen. No match is a transient during the overlay's DMA, not a mode — hold the last known id.

Source rects are in bottom-screen pixels (256×192). Elements are drawn at PSZ_HUD_SCALE (default 2.0) in window pixels, not DS pixels — so raising the output resolution gives them a smaller share of the screen rather than scaling them up with it.

The target box hides itself

The game draws that box whether or not anything is locked on, and there is no flag for it. Emptiness is detected by counting dark pixels in the box interior: text is near-black, an empty panel is not. Expected: present with a name and attribute when something is targeted, entirely absent otherwise — confirmed both ways, in a field and in town.

Menus, shops and the counter specified

Expected: the corner elements disappear entirely; the bottom screen is drawn centred at PSZ_MODAL_SCALE (default 0.66) over the field dimmed by PSZ_MODAL_DIM (default 90/255).

Why 66% and not full-screen: these are split scenes. The top screen carries real content — the race description in character create, the "Select an area." prompt at the counter, the logo at the title — and covering it hides information the dual-screen original shows. The menu must be readable and the top screen must remain readable.

PSO-style menu opt-in

PSZ_MENU_PSO=1 stops presenting the menu as a screen-shaped thing on top of the game and spreads its own panels to the edges instead: the player strip top-left, the heading top-centre, the description top-right, the command list down the left, the stats panel bottom-right. The field stays visible between them.

Source rects are the main menu's panels measured at native resolution, each overridable (PSZ_MENU_LIST, PSZ_MENU_DESC, PSZ_MENU_STATS, PSZ_MENU_TITLE, PSZ_MENU_WHO).

Main menu only, which is why it is opt-in. Nothing yet identifies which menu is open, so the item menu and the Mag screen would be sliced by rects that do not describe them. Identifying the open menu is the work that would make this the default.

Single-screen output specified

The area map is the one element that is reconstructed rather than copied, because the game's own area map is a full-screen touch-gated modal that only exists while open — there is nothing on screen to copy. Cells come from the room table; exits are stubs, and keyed or enemy-gated exits are drawn red.

Android: no overlay under OpenGL bug

MelonInstance.cpp guards the overlay with if (!isRendererAccelerated), so with the OpenGL renderer it never runs and the accelerated branch is a literal "Do nothing". One cause, two symptoms: no HUD elements at all on GPU, and the pre-game screens showing whatever melonDS-android's own layout does rather than our policy.

It cannot be fixed by moving the call — in the accelerated path the frame lives in a GL texture and Composite() needs CPU framebuffers. Android needs a real drawing path, the same shape as the Qt one.

Implemented, not yet confirmed on device. PSZOverlayGLES draws the same Frame into the frame texture, so the accelerated branch no longer does nothing. The texture holds both screens stacked, and sampling a texture while rendering into it is undefined, so it copies the bottom screen to a scratch texture first — one copy per frame, and only on frames that draw. This is written and it compiles; nobody has seen it run. It stays tagged as a bug until a device confirms it.

HUD elements: rects are the wrong primitive direction change

Two problems with copying rectangles out of the bottom screen, both reported from the device:

  • They are too large. Android composites at DS resolution, where a 70px panel is 27% of the screen at any output size.
  • The game's panels are not rectangles. They have rounded and notched frames, so a rectangular clip drags in background around the edges. No choice of rect fixes that.

The direction is our own artwork with alpha — PNG elements drawn over the scene, fed by values already read from RAM — plus a size control. Both need a drawing path that can scale and blend, which is the same missing piece as the OpenGL bug above.

Size control: PSZ_HUD_ELEMENT_SCALE, 1.0 being DS-native. Elements are now sized as a fraction of the top screen rather than a fixed pixel multiple, so they no longer grow relative to the scene as output resolution rises.

Artwork is not committed here, deliberately. The PNGs exist in psz-godot, cut from the game's own sprites — and git ls-files shows they are not tracked there either, even though that repo is public. They ship through its asset pack instead. Committing PSZ-derived art into this public GPLv3 repo would break a rule the project already follows everywhere else: no ROM, no game assets, no savestates. So the loader reads them from a gitignored directory and a script populates it from a local psz-godot checkout. How release builds get the artwork is an open decision, not an oversight.

Android: no layout configuration specified

A fresh install MUST open top-screen-only, centred, filling the display. No layout editing, and no bottom window to try to remove.

Previously the default layout placed both screens, so reaching the only state this build supports meant hand-building a layout — and the bottom window could not be deleted from it at all. buildSingleScreenLayout() already existed upstream but was reachable only on dual-display devices; the single-display path now uses it too.

Known cost: that layout carries no soft input buttons, so a touch-only device loses on-screen controls. Handhelds with physical controls — what this build targets — are unaffected. -Dpsz.dualScreen=true restores the old behaviour.

Earlier reported bugs all fixed

All three come from one root cause, so they should be fixed together rather than patched individually. The current rule presents the bottom screen whenever *(0x02108D04) == 0 or *(player+0x280) == 5. That conflates two different situations:
  • the bottom screen is the interaction — menus, shop, counter, file select, character create. Presenting it is right.
  • the top screen is the content — cutscenes, dialogue, the title. Presenting the bottom screen actively hides what the player is supposed to be looking at.
The rule cannot tell them apart, so it gets the second class wrong every time.
#StateExpectedActual
1Title show the top screen's logo FIXED — ov00. Verified: the logo fills the screen.
2Cutscenes — the opening one before the title, and the one after character creation show the top screen, where the cutscene plays FIXED — ov16. Verified on the captured opening-cutscene savestate.
3Dialogue show the top screen, where the dialogue is drawn FIXED — ov17. Verified on the captured Kai dialogue savestate.

Two pixel heuristics failed before the mode was read directly

Both are recorded because each looked verified before it was tested on the case that mattered.

  • Colour variety assumed a cutscene's bottom screen is close to a flat fill. It is the densest of the three states measured (0.82, against 0.69 for file select and 0.64 for create) — a large pastel panel. It passed review only because it was first tried on the SEGA splash, which really is blank.
  • Dark-text density fixed the cutscenes and then hid the "This character will be created. Is that OK?" confirmation, because that prompt is small text on a white panel. Trading three bugs for a new one.

Both were inferring the mode from what came out of the renderer. The overlay slot is the mode, so it is read directly and no threshold exists to tune.

What the captures settled

Two savestates — the opening cutscene and the Kai dialogue — put them in ov16 and ov17, both with a NULL player object. That also refuted this project's own assumption that dialogue ran inside ov04 with control mode 5, which is why every earlier fix targeted the wrong branch.

Reporting a bug

Include the state name from this page, what you expected from it, and what you saw. If the two agree and the behaviour is still wrong, that is a spec change and should say so — those are the reports worth having, because they are the ones this page cannot answer on its own.
